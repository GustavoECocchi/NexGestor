## Achado novo — fonte parcialmente associada ainda aceita (P1)

Local: `app/service/benchmark_service.py`, `_localizar_fonte_associada`,
linhas 524–550 no HEAD analisado.

A função calcula cobertura integral usando TODOS os segmentos que tocam
o número. Só depois elimina índices/chunks inválidos para selecionar a
URL. Assim, segmentos sem fonte válida completam artificialmente a
cobertura de uma fonte que sustenta apenas parte do valor.

Reprodução sem rede, com objetos reais do SDK e helper existente da suíte:

```python
from test_benchmark_mercado import _resposta
from app.service.benchmark_service import _interpretar_resposta

for indices in ([], [99], [1]):
    resposta = _resposta(
        ["VALOR: 12.34"],
        supports=[(0, 7, 8, [0]), (0, 8, 12, indices)],
        chunks=["https://fonte.example/relatorio", None],
    )
    resultado = _interpretar_resposta("ctr_link", resposta)
    print(resultado.encontrado, resultado.value, resultado.fonte_url)
```

Nos três casos: `True`, `12.34`, `https://fonte.example/relatorio`.
A única fonte válida cobre `[7,8)`, um byte dos cinco de `12.34`.
O restante tem lista vazia, índice inexistente ou chunk sem web.
Esperado: rejeição como `BenchmarkFalhaTransitoria`.

Impacto: referência aparentemente verificada pode ter sustentação parcial;
o score não é afetado pelo desenho informativo. Não se demonstrou frequência
desse formato no Gemini real nem exploração em produção. A feature nasce
desligada, mas a invariável declarada está quebrada no código atual.

Correção recomendada: associar intervalos às fontes válidas antes de medir
cobertura, exigir cobertura integral da URL aceita e manter rejeição de
ambiguidade. Acrescentar as três regressões acima e revisar a versão do
cache para invalidar positivos aceitos pela regra defeituosa. Nenhuma
correção de produto foi executada neste pedido de análise.

### Correção do achado P1 (fonte parcialmente associada)

`app/service/benchmark_service.py`, `_localizar_fonte_associada`: a
cobertura integral do trecho do número era calculada somando TODOS os
segmentos que tocavam o número, mesmo os sem chunk/fonte válida — um
segmento sem fonte "completava" a cobertura de um vizinho que sustentava só
uma fração do valor. Corrigido: um segmento só entra no cálculo de
cobertura se ele mesmo citar ao menos um `grounding_chunk` válido (índice
dentro da faixa, com `web.uri` http(s) válido). `storage.REGRA_BENCHMARK_VERSAO`
subiu de 1 para 2, invalidando qualquer linha de cache gravada sob a regra
antiga.

### Teste de rede real — 3 chamadas, dentro do limite de R$15

Backend local (`uvicorn`) rodando com o `.env` real. Primeira tentativa
falhou com **401 UNAUTHENTICATED** — a key colada no `.env` não tinha o
formato de API key do AI Studio (`AIzaSy...`); o usuário corrigiu a key
(sem eu ver o valor em nenhum momento, só confirmei o formato dos 6
primeiros caracteres). Segunda tentativa, já com a key certa, falhou com
**400 INVALID_ARGUMENT: "Manually set deadline 8s is too short. Minimum
allowed deadline is 10s."** — achado real, não um erro de configuração
do teste: a API do Gemini exige deadline ≥10s para chamadas que usam o
tool de busca (`google_search`), e `GEMINI_TIMEOUT_SECONDS=8.0` (o padrão
do projeto, usado sem problema pela análise principal SEM grounding)
quebrava 100% das buscas reais do benchmark.

Corrigido em `benchmark_service.py`: a chamada de grounding passa a usar um
`http_options=types.HttpOptions(timeout=_TIMEOUT_BUSCA_MS)` PRÓPRIO
(12.000ms, com margem de 2s sobre o mínimo documentado) só na config da
chamada com `google_search`, em vez de depender do timeout padrão do
client compartilhado (`ai_service._get_client`) — evita mudar o orçamento
de espera da análise principal por uma exigência que só existe para
grounding. `_fake_client` dos testes é `MagicMock`, não afirma os kwargs
exatos da chamada — suite continuou verde sem alteração (113/113 em
`test_benchmark_mercado.py`, 1677/1677 no total).

Com o timeout corrigido, as 3 buscas reais (`ctr_link`) devolveram 200:

|---|---|---|---|
| `ecommerce_varejo` | `meta_ads` | `encontrado=false`, `motivo_tipo=nao_encontrado` | 1.63s |
| `software_tecnologia_b2b` | `google_ads` | `encontrado=false`, `motivo_tipo=nao_encontrado` | 1.79s |
| `moda_vestuario` | `meta_ads` | `encontrado=false`, `motivo_tipo=nao_encontrado` | 1.84s |

Cache SQLite (`data/benchmark_local_test.db`, artefato local, apagado ao
